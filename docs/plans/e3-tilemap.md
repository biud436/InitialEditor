# E3: 맵 편집 (타일맵 확장)

**권장 모델**: Claude Opus 5. 옛 코드의 로직을 정해진 확장 API로 옮기는 작업이며, 설계는 [04-extensions-and-tilemap.md](04-extensions-and-tilemap.md)에서 끝났다.
확장 API가 부족해 코어를 고쳐야 하는 지점이 나오면 그때 Fable 5로 승격한다.

> 목표 (2026-09-26 개정): **알데바란 숲 스테이지를 에디터에서 열어 타일을 고치고 늑대를 옮긴 뒤, 그 자리에서 실행해 그 판을 돈다.**
> 옛 목표(옛 에디터의 기능 이전, 타일맵이 씬의 오브젝트가 되는 것, `events` 보존)는 그 뒤에 따라온다.

## 방향을 바꾼 이유

E0 와 E1 을 본 저자의 판정은 "그럴싸하긴 한데 실제로 별 도움이 안 된다", "단순 스크립트 에디터로는 아무것도 할 수 없다" 였다.
스크립트 편집과 실행은 VS Code 와 터미널로 이미 하는 일이다. 에디터가 값어치를 가지는 자리는 텍스트로는 못 하는 일이다.

- 알데바란의 맵(`aldebaran_forest.json`, 256x28 타일)은 생성기가 만들고 손으로는 못 고친다
- 몬스터 배치는 `stages/forest.lua` 의 숫자 표이고 같은 표가 Ruby 판에도 한 벌 더 있다
- 고친 것을 확인하려면 그 자리까지 걸어가야 한다

그래서 이 단계의 첫 결과물은 그 셋을 푸는 것이다.

## 설계 (2026-09-26)

- **맵 파일의 오브젝트 레이어.** 맵 포맷 v2 에 `objects` 배열(픽셀 좌표, 타입, props)을 둔다. 엔진 C++ 은 모르는 키를 무시하므로 무수정이다. 알데바란의 시작 지점, 체크포인트, 몬스터(종과 순찰 범위), 흔적(글), 구간이 여기로 오고, 스테이지 모듈(Lua 와 Ruby)은 맵에서 읽는다. 게임 쪽 작업의 이름은 M1(엔진 저장소)이다.
- **오브젝트 스키마.** 타입과 칸과 모양(점, 띠, 사각형)과 색은 프로젝트의 `resources/schema/map-objects.json` 이 정한다. 에디터는 이것으로 맵 위의 표식과 인스펙터 폼을 만든다. 코어는 장르를 모른다.
- **맵 모델은 순수 TS.** `packages/ext-tilemap/src/model/` (포맷, 타일 계산, 명령, 스키마, 문서). 저장 형식은 고정이다: 2칸 들여쓰기 JSON, 타일 배열은 맵 한 줄을 한 줄에. 엔진의 맵 생성기도 같은 형식으로 쓰고 `objects` 를 보존한다.
- **여기서 실행.** 스키마의 `play.env` 가 실행 환경 변수를 정한다 (알데바란: 스테이지와 시작 x). 에디터는 선택한 오브젝트나 커서 자리의 x 로 채워 엔진을 띄운다.
- **UI 는 앱 안에.** 확장 API 에 문서 뷰와 인스펙터 등록이 아직 없어, 맵 뷰와 패널은 씬 도구처럼 `packages/app` 에 둔다. 모델은 확장 패키지에 있다.

## 위험

- **옛 `tilemap.ts`에 숨은 규칙.** 1,052줄 갓 클래스에 렌더링과 데이터와 입력이 섞여 있어 옮기다 놓치는 규칙이 있을 수 있다. 대응: 마일스톤 2에서 데이터 로직만 옮기고, 옛 에디터와 같은 입력에 같은 배열이 나오는지 비교 테스트를 둔다.
- **성능.** PIXI 8에서 타일을 스프라이트 하나씩 그리면 큰 맵이 느리다. 대응: 마일스톤 4의 기준을 알데바란 맵으로 잰다. 필요하면 레이어 렌더 텍스처.
