# 에디터를 끝낸 뒤의 목표

> 작성일: 2026-09-27 (저자 요청).
> 지금 목표(에디터 완성)는 바뀌지 않는다. E5를 마치고 `v2.0.0-alpha.1` 프리릴리스를 낸 뒤에 아래 셋을 저자가 적은 순서대로 시작한다.

| 목표 | 크기 | 엔진도 고치는가 |
|---|---|---|
| 1. 프로젝트 뷰 필터 | 소 | 아니다 |
| 2. 스크립트 매개변수와 컴포넌트 | 대 | 고친다 (씬 로더 둘과 씬 포맷 문서) |
| 3. 비주얼 스크립팅 검토 | 검토 문서는 소, 만들면 대 | 방식 A, B는 고친다 (두 언어의 실행기) |

언어 서버(LSP)는 따로 이슈 [#53](https://github.com/biud436/InitialEditor/issues/53)에 정리했다. 이것도 에디터를 끝낸 뒤에 한다.

## 1. 프로젝트 뷰 필터

원하는 것: 프로젝트 뷰(파일 목록)에서 프로젝트 파일이 아닌 것을 걸러 낼 수 있어야 한다.

지금:
- Tauri 앱과 브라우저 폴더 모드는 폴더의 파일을 전부 보여 준다. 거르는 코드도, 무시 파일이나 설정도 없다. 엔진 저장소를 열면 최상위에만 53개가 보이고, 게임 뷰가 올리는 파일은 200개쯤인데 전체는 1만 2천 개가 넘는다(`.git` 제외).
- 브리지 모드만 엔진 브리지의 허용 목록(`game.json`, `scripts/`, `resources/`, `.initial-editor/`)으로 거른다 (`tools/bridge/lib/files.js`).
- 무엇을 볼지는 기능마다 따로 정한다. 게임 뷰 스테이징(`gameView/staging.ts`)은 `game.json`, `scripts/`, `resources/`에서 `resources/rtp`, `resources/aldebaran/src`, 점으로 시작하는 이름, `*.zip`, `*.psd`를 빼고, 찾기(`find.ts`)는 `scripts/`와 `resources/`를, 자산 목록(`projectAssets.ts`)은 `resources/`와 `scripts/<언어>/components/`를 본다.

제안:
- 기본 규칙은 엔진이 읽는 `game.json`, `scripts/`, `resources/`로 한다. 규칙은 코어 한 곳에 두고 찾기와 스테이징도 같이 쓴다.
- 백엔드는 그대로 두고 거르는 일은 뷰 모델(`projectTree.ts`)이 한다. 그래야 세 백엔드에서 결과가 같다.
- 프로젝트 뷰 위쪽에 필터 단추를 두고, 켜고 끈 상태는 프로젝트마다 `.initial-editor/`에 남긴다.
- 게임마다 더 빼거나 넣을 것은 무시 파일(예: `.initial-editorignore`, `.gitignore`와 같은 문법)로 받는다.

정할 것:
1. 걸러진 항목을 숨길까, 흐리게 보여 줄까. 필터를 처음부터 켜 둘까.
2. 어디까지 프로젝트 파일로 볼까. `resources/` 안의 작업 파일(`resources/aldebaran/src`, `*.psd`, `*.zip`), `resources/rtp`(게임이 읽지만 git에 올릴 수 없다), 게임의 `README.md`, `LICENSE`, `docs/`, `.gitignore`, 그리고 `.initial-editor/` 폴더.
3. 무시 파일을 프로젝트 최상위(커밋된다)에 둘까, `.initial-editor/`(새 프로젝트의 `.gitignore`가 뺀다) 안에 둘까. `.gitignore`도 따를까.

## 2. 스크립트 매개변수와 컴포넌트

원하는 것: 스크립트의 매개변수를 보고 고치는 속성 뷰가 있고, Unity나 Godot처럼 오브젝트에 컴포넌트를 여러 개 붙이고 뗄 수 있어야 한다.

지금:
- 여러 개 붙이기는 이미 된다. 씬 포맷 v1의 오브젝트는 `scripts`에 컴포넌트 논리 이름의 배열을 갖고, 엔진의 두 로더(`scene_loader.lua`, `scene_loader.rb`)는 배열 순서대로 돌린다.
- 매개변수를 선언하는 방법이 없다. 컴포넌트는 오브젝트의 `props`에서 키를 바로 읽고(플래피 `scroller`의 `kind`, `pipes`의 `after`, 샘플 `mover`의 `target`, `dx`, `dy`, `limit`), 기본값은 코드 안에 흩어져 있다. 한 오브젝트의 컴포넌트들이 `props` 하나를 같이 쓴다.
- 인스펙터의 스크립트 목록(`InspectorPanel.tsx`의 `ScriptsSection`)은 붙이기, 떼기, 열기만 한다. 같은 이름은 두 번 붙일 수 없고 순서는 못 바꾼다. 타입 인스펙터가 모르는 `props` 키(`kind`, `after`)는 파일에 보존될 뿐 화면에 보이지 않는다.
- 붙이기 대화상자의 제안 목록은 `components/` 아래 파일을 전부 올려서 `flappy/common` 같은 도우미 모듈도 섞인다.
- Lua 컴포넌트는 모듈 하나를 모든 오브젝트가 같이 쓴다. Ruby는 오브젝트마다 인스턴스를 만들지만 `new`에 인자가 없고, 클래스 이름을 경로의 마지막 부분으로 정해서 `components/a/bird`와 `components/b/bird`가 같은 `Bird`가 된다.
- 선언된 필드로 폼을 그리는 선례가 있다. 맵 오브젝트 스키마(`resources/schema/map-objects.json`)와 그 인스펙터이고, 폼 입력은 E5에서 `packages/ui`의 `SchemaFieldInput`으로 옮겨진다.

제안:
- 매개변수 선언은 언어와 무관한 JSON 파일로 컴포넌트 옆에 둔다. Lua와 Ruby가 한 파일을 같이 쓰고 소스를 해석할 필요가 없다. 필드 형식은 맵 오브젝트 스키마를 따르고, `after`와 `target`에 쓸 씬 오브젝트 참조 형식을 더한다.
- 씬 파일은 오브젝트에 `params` 키를 더한다 (`{"components/flappy/scroller": {"kind": "ground"}}`). v1 로더는 모르는 키를 무시하고 에디터는 보존하므로 판을 올리지 않아도 된다.
- 엔진의 두 로더는 선언의 기본값에 오브젝트의 값을 덮어 컴포넌트마다 따로 넘긴다 (Lua는 훅 인자나 컴포넌트별 표, Ruby는 `new(params)`). Ruby 클래스 이름은 전체 경로로 정한다. 씬 포맷의 정본은 엔진 `docs/plans/r1-scene-loader.md`이므로 그 문서를 먼저 고친다.
- 인스펙터는 붙은 컴포넌트를 순서대로 보여 준다. 컴포넌트마다 제목 줄(이름, 접기, 위아래로 옮기기, 떼기)과 선언된 필드의 폼이 있다. 제안 목록에는 선언이 있는 파일만 올린다.
- 둘로 나눌 수 있다. 순서 바꾸기는 에디터만 고치면 되니 먼저 하고, 매개변수는 엔진과 함께 뒤에 한다.

정할 것:
1. 선언을 JSON 파일로 둘까, 스크립트 안(Lua `M.params`, Ruby `PARAMS`)에 둘까. 후자는 쓰기 편하지만 두 언어의 선언을 따로 맞춰야 하고, 에디터가 소스를 해석하거나 엔진에 물어야 한다.
2. 오브젝트의 값을 새 키 `params`에 둘까, `scripts` 항목을 객체로 바꿔 씬 포맷 v2로 갈까.
3. 같은 컴포넌트를 한 오브젝트에 두 번 붙일 수 있게 할까. 지금 엔진은 막지 않지만 Lua에서는 같은 모듈이 같은 `obj`로 두 번 불린다.
4. 기존 `props`의 키(`kind`, `after`)는 매개변수로 옮길까, 둘 다 읽게 둘까.
5. 실행 중인 게임의 값도 보여야 할까 (Unity의 플레이 모드처럼). 그러려면 엔진에서 값을 받아 오는 방법이 새로 필요하다.

## 3. 비주얼 스크립팅 검토

원하는 것: 비주얼 스크립팅을 고려한다. 만들지는 검토 뒤에 정한다.

전에는 하지 않기로 했던 것이다 ([index.md](index.md) 6절, [02 문서](02-scope-and-screens.md) 2절, 엔진 `docs/plans/roadmap-v2.md`). 이벤트 커맨드 목록이 그 일을 한다는 이유였고, 저자 요청(2026-09-27)으로 다시 연다.

지금:
- 가장 가까운 것은 RPG 이벤트 커맨드 목록이다 (`resources/schema/event-commands.json`, `scripts/lua/rpg/commands.lua`와 `interpreter.lua`, E5의 커맨드 목록 편집기). 커맨드 17종 중 장르와 무관한 것은 9종이다(`wait`, `if`, `setFlag`, `setVar`, `playSe`, `playBgm`, `scene`, `script`, `comment`). 다만 `if`의 아이템 조건은 RPG 것이고, 트리거 넷(`action`, `touch`, `auto`, `parallel`)은 맵과 플레이어를 전제한다.
- Ruby에는 이벤트 실행기가 없다.
- 플래피 `bird`(`scripts/lua/components/flappy/bird.lua`)처럼 매 프레임 상태와 물리를 다루는 로직은 순서대로 도는 목록으로 적기 어렵다. 시작, 매 프레임, 키 입력, 타이머, 충돌 같은 훅이 있어야 한다.
- 노드 목록과 코드 생성에 쓸 명세는 있다. `resources/api/initial2d-api.json`이 모든 함수의 Lua 이름, Ruby 이름, 인자 타입을 적고, 두 언어의 표면 테스트가 이것을 바인딩과 대조한다.
- 어느 방식이든 `ext-rpg` 밖에 있어야 하고 `event-commands.json`이 없는 프로젝트에서 돌아야 한다 (RPG 개념은 코어에 넣지 않는다).

검토할 방식 셋:

| 방식 | 그대로 쓰는 것 | 새로 만들 것 |
|---|---|---|
| A. 커맨드 목록을 RPG에서 떼어 범용으로 | 목록 포맷, 컴파일과 검사, E5의 목록 편집기 | 실행기와 편집기를 범용과 RPG로 나누기, Ruby 실행기, 범용 트리거. 매 프레임 로직은 여전히 `script` 커맨드로 넘긴다 |
| B. 노드 그래프 JSON을 두 언어가 해석 | 스키마 폼, API 명세로 만든 노드 목록 | 새 포맷, 해석기 둘과 에디터 검사기(같은 규칙을 세 번 구현), 그래프를 실행하는 범용 컴포넌트, 캔버스 편집기. 노드 좌표 때문에 diff를 합치기 어렵고 매 프레임 해석 비용이 든다 |
| C. 그래프에서 Lua와 Ruby 소스를 생성 | 기존 컴포넌트 실행, 저장 시 핫 리로드, 오류 줄 링크, API 명세의 두 언어 이름 | 언어별 생성기 둘, 생성된 줄과 노드의 대응표, 생성 파일의 커밋 규칙과 손 편집 금지 규칙. 그래프 JSON의 diff 문제는 B와 같다 |

정할 것:
1. 누구를 위한 것인가. 스크립트를 쓰지 않는 사람이 게임 하나를 끝까지 만드는 도구라면 B나 C, 스크립트를 쓰는 사람이 연출과 흐름을 빨리 적는 도구라면 A가 맞다.
2. 두 언어에서 똑같이 돌아야 하는가. 그렇다면 C가 유리하다. 생성된 코드는 보통 컴포넌트로 돌고, 두 언어 판을 같은 엔진 검사로 견주면 된다 (플래피의 Lua 판과 Ruby 판을 같은 항목으로 보는 `check_flappy_run`이 선례).

첫 단계는 만들기가 아니라 짧은 검토 문서다. 플래피 `bird` 하나를 A와 C로 적어 보고(A는 커맨드 목록 JSON, C는 그래프 JSON과 생성될 Lua, Ruby 코드. B의 그래프는 C와 같다), 저자가 읽고 고른다.
